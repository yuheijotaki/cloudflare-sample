Cloudflare Early Hints

結論: ビルドした静的ファイルには効果がほぼない(もともと速い)。コードが時間をかけて生成する応答には効く。

0. 登場人物

Cloudflare を使ったサイトでは、オリジンとブラウザの間に Cloudflare のエッジが入る。エッジは世界中にあり、ユーザーに近い場所でリクエストを受ける。以降の図はすべて「オリジン → エッジ → ブラウザ」の左から右で描く。

1. 仕組み

通常、ブラウザは HTML が届くまで何もできない。103 Early Hints は、本体の 200 より先に Link ヘッダーだけを送り、オリジンが HTML を作っている間にブラウザへ CSS を先読みさせる。

103 を返しているのはオリジンのコードではなく、エッジ。コード側に Early Hints の記述は一切ない。

  • オリジンは、通常の 200 応答に Link: </styles.css>; rel=preload を付けるだけ。
  • エッジは HTML の応答からその Link を覚える(CSS など HTML 以外の応答は見ない)。
  • 次回以降、エッジはリクエストをオリジンに転送すると同時に、覚えていた Link を 103 として先に返す。

2. 検証: 静的ファイルとコード生成の応答で比べる

同じ Pages プロジェクトに 3 つのページを置いた。静的 HTML、コード生成の HTML、そして比較用に Link を付けないコード生成の HTML。Link ヘッダーの付け方は応答の種類で変わる。

URL応答の種類Link の付け方103本体の到着効果
/ ビルドした静的 HTML public/_headers の /* ルール 出る 約 100 ms ほぼなし。本体がすぐ届くので先読みの出番がない
/pages-function functions/ のコードが 1 秒かけて生成 コード内で Response に付ける(_headers は Function の応答には効かない) 出る 約 1.1 s あり。CSS の取得開始が約 1 秒早まる
/pages-function-no-hints 同上(比較用) 付けない 出ない 約 1.1 s なし。CSS の取得は HTML 到着後に始まる

「103 が出る」と「効く」は別。静的ファイルでも 103 は出るが、本体が 100 ms で届くので稼げる時間がない。効くのは本体の生成に時間がかかる応答だけ。

もう 1 つ、ブラウザ側で引っかかった点がある。103 で先読みした CSS はブラウザの HTTP キャッシュに入る。HTML を解析して同じ CSS が必要になったとき、キャッシュが期限切れだと取り直しになり、先読みが無駄になる。

3. Chrome DevTools での確認

  • Network パネルの「Disable cache」をオフにする。オンだと先読みしたキャッシュが使われない。
  • HTML の行を選ぶと、Headers タブに「Early hints headers」が出る。これが 103 で届いた Link。103 を受け取るのは HTML のリクエストだけ。
  • styles.css の行の Initiator が Early-hints になる。CSS 自体に 103 が返ったのではなく、「HTML の 103 がきっかけで取りに行った」という意味。Size が (disk cache) なら先読みが使われている。

4. 使いどころと注意点

  • 効く: SSR など、生成に時間がかかりキャッシュできないページ。
  • 効かない: 静的ファイルや、CDN キャッシュから即座に返るページ。
  • デプロイ先: workers.dev では出ない。Pages は自動で有効。カスタムドメインは Speed 設定で ON にする。
  • 学習待ち: デプロイ直後は出ない。今回は約 3 分かかった。
  • 先読み対象のキャッシュ: Cache-Control が短いと取り直しになり無駄になる。
  • プロトコルとブラウザ: HTTP/2 か HTTP/3 のみ。Safari は preconnect だけ対応。
