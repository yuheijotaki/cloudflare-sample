Cloudflare Early Hints を実際に動かして分かったこと

103 Early Hints の仕組み、Cloudflare が「オリジンの代わりに」ヒントを出す方法、そして今日の検証で 103 が出た場所と出なかった場所の理由を図で整理する。

1. Early Hints とは: サーバーの「考え中」の時間を使う

HTML を生成するのに時間がかかるサーバーは、その間ブラウザを待たせている。RFC 8297 の 103 Early Hints は、本体の 200 より先に「この CSS とフォントが必要になる」という Link ヘッダーだけを送り、ブラウザにその待ち時間で先読みさせる仕組み。

対応はブラウザ側にも必要で、Chrome は 103 以降デフォルトで有効。HTTP/2 または HTTP/3 のみで動作し、HTTP/1.1 では無視される(Chrome Developers)。Safari は preconnect のみ対応で preload は未対応。

2. Cloudflare の方式: オリジンは 103 を喋らなくていい

多くのアプリケーションサーバーは 103 を返せない。Cloudflare の設計は「エッジがオリジンの Link ヘッダーを学習して覚え、次回以降はオリジンに届く前にエッジが 103 を返す」というもの。オリジン側の変更は Link ヘッダーを付けるだけで済む。

学習の対象になるのは次を全て満たすレスポンスだけ(公式ドキュメント)。

  • URI が .html / .htm / .php で終わるか、拡張子なし
  • ステータスが 200 / 301 / 302
  • Link ヘッダーに rel=preload または rel=preconnect がある

3. 103 が出る条件: 今日の 3 つの環境で何が違ったか

同じ _headers ファイルを使っても、デプロイ先によって結果が変わった。リクエストが 103 を受け取るまでには 3 つの関門がある。

環境ゾーンLink ヘッダー103止まった関門
cloudflare-sample.yuheijotaki.workers.dev
Workers 静的アセット + 1 秒遅延の /slow		workers.dev(Cloudflare 所有)あり出ない1
cloudflare-sample-pages.pages.dev
同じ dist + Pages Function の /slow		pages.dev(自動有効)あり出るなし
recruit.smarthr.co.jp
Workers + カスタムドメイン、HTML を CDN キャッシュ		smarthr.co.jp(自社)あり(preconnect)観測できず2(外からは 1 と区別不能)

本番サイトで 103 が出ないのは故障ではない。 HTML が CDN キャッシュから数十 ms で返るなら、103 を先に送る意味がない。Early Hints が効くのは「生成に時間がかかり、キャッシュできないページ」。SSR 応答や、キャッシュ MISS になった POP の初回リクエストがそれに当たる。

4. ブラウザ側の落とし穴: 先読みしたものがキャッシュで使えるか

サーバーが 103 を返し、Chrome がそれを受け取っても、まだ効かないケースがあった。Chrome は 103 で指定されたリソースを HTTP キャッシュに入れ、HTML を解析して同じ URL が必要になった時点でキャッシュから取り出す。この取り出しが「新鮮なキャッシュ」として成立するかは、リソース側の Cache-Control で決まる。

5. 確認方法

curl: 103 が先に返るかを見る

--http2 を忘れると HTTP/1.1 になり、絶対に 103 は出ない。

$ curl -sv --http2 -o /dev/null https://cloudflare-sample-pages.pages.dev/slow 2>&1 | grep -E '^< (HTTP|link)'
< HTTP/2 103
< link: </styles.css>; as=style; rel=preload
< HTTP/2 200
< link: </styles.css>; rel=preload; as=style

Chrome DevTools: ブラウザが実際に使ったかを見る

  1. Network パネルで「Disable cache」をオフにする。Early Hints はブラウザキャッシュを経由するので、オンにすると効果が消える。
  2. URL バーから対象ページを開く(トップレベルナビゲーションのみ対象。iframe やサブリソースへの 103 は無視される)。
  3. ドキュメントの行を選び、Headers タブに「Early hints headers」セクションが出ていれば、Chrome は 103 を受け取っている。
  4. 一覧の styles.css の Initiator 列が Early-hints、Size が (disk cache) なら、先読みが使われている。

Console で確定させるなら次を実行する。

performance.getEntriesByType('resource')
  .filter(e => e.name.includes('styles.css'))
  .map(e => ({ initiatorType: e.initiatorType, transferSize: e.transferSize }))
// → [{ initiatorType: "early-hints", transferSize: 0 }]

設定: _headers ファイル

Workers 静的アセットでも Pages でも、public/_headers に置けばビルド出力にコピーされる。

/*
  Link: </styles.css>; rel=preload; as=style

# 先読みした CSS をブラウザキャッシュから再利用できるようにする
/styles.css
  Cache-Control: public, max-age=3600

_headers は静的アセットの応答にしか効かない。SSR やミドルウェアが生成する応答には、Worker コード側で同じ Link ヘッダーを付ける必要がある(Workers docs)。

6. まとめ

  • 仕組み: エッジが Link ヘッダーを学習し、次回からオリジン到達前に 103 を返す。オリジン側は Link を付けるだけ。
  • 効く場面: 生成に時間がかかり、キャッシュできない HTML。今日の /slow では CSS の取得開始が約 1 秒早まった。
  • 効かない場面: HTML が CDN キャッシュから即答できるページ。103 が出ないのは「すでに速い」というサイン。
  • デプロイ先: workers.dev では出ない。Pages は自動有効。カスタムドメインはゾーンの Speed 設定で ON にする。
  • 学習の遅れ: デプロイ直後は出ない。今回は約 3 分。
  • preload 対象のキャッシュ: Cache-Control が短いと再検証が走り、先読みが無駄になる。
  • その他の制約: HTTP/1.1 不可、クエリ文字列は無視、Chrome は最初の 103 だけ処理、Safari は preconnect のみ。ログに出る ClientRequestSource: earlyHintsCache の 504 はヒント収集のプローブで正常。
